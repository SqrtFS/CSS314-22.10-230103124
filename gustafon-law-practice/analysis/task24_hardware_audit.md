## 3. How to read it, and why this dataset does NOT demonstrate Gustafson's law

**The sandbox has one hardware thread.** Every thread count above 1 is *oversubscribed*: the OS time-slices `P` threads over a single core, so wall-time is ≈ `P × T(1)`, and scaled speedup is ≈ 1. The regression then reports `α ≈ 1`, i.e. "the machine behaves as if fully serial". That is the correct statement about *this hardware*, but it says nothing about the benchmark's algorithmic serial fraction. Do not quote `α = 0.997` as a property of the code.

Two details in the data are explained by the model:

1. **`S` slightly above 1 (1.02–1.035).** The benchmark has a fixed serial initialisation `t_s ≈ 5.8 ms` that does *not* grow with `P`, and parallel work `t_p ≈ 152 ms` per thread. On one core `T(P) = t_s + P·t_p`, so `S(P) = P(t_s+t_p)/(t_s+P·t_p) → (t_s+t_p)/t_p = 1.038`. Observed 1.028–1.035 fits. This is Gustafson's mechanism (constant serial time, scaled work) operating on a machine with no parallelism to exploit.
2. **`R²` is negative / meaningless** in the fit output because `S(P)` is nearly constant, so there is no variance for the model to explain.

**Prediction for a real multi-core host** (not measured here): with `t_s/T₁ = 5.8/157.7 = 3.7 %`, expect `α ≈ 0.037`, `S(P) ≈ P − 0.037(P−1)` up to the point where memory bandwidth and thermal limits intervene. Run `python3 run_bench.py` on such a machine and compare, then add the CPU/cache/NUMA table of that machine to this audit.

## 4. Expected deviations on real hardware (checklist)

| Effect | Mechanism | Signature in data | How to test / control |
|---|---|---|---|
| **Thermal throttling / turbo** | All-core boost lower than 1-core boost; heat → frequency drop | `T(1)` faster than `T(P)` with no `α`; run-to-run drift, later runs slower | Log frequency (`turbostat`, `cpupower monitor`); fix governor `performance`; interleave runs (already done); cool-down between runs |
| **NUMA boundaries** | Threads on socket 1 touching memory on socket 0 (remote latency 1.5–2×, bandwidth penalty) | A step in `T(P)` when `P` exceeds cores per socket | `numactl --hardware`; `OMP_PROC_BIND=close OMP_PLACES=cores`; first-touch initialisation; compare `numactl --interleave=all` |
| **SMT (hyper-threads)** | 2 threads share ALU/L1; per-thread throughput ≈ 60–70 % | Slope drops after `P` = physical cores | Run `P ≤` physical cores separately; report both |
| **Shared L3 / memory bandwidth** | Cache and DRAM channels shared | Superlinear `T(P)` for bandwidth-bound kernels | This kernel is compute-bound (no large arrays in the parallel part), so expect minimal effect; test with STREAM |
| **Hypervisor steal time / noisy neighbours** | vCPUs descheduled | Outliers, high std | `top` steal column; repeat runs; report medians |
| **Thread start-up and barrier** | `O(log P)` OpenMP fork/join | Small constant added to `α` | Increase `k` |

## 5. What to include in the final submitted audit

1. Output of `lscpu`, `lscpu -C` (cache), `numactl --hardware`, `lstopo --of txt`, `dmidecode -t memory | grep -E "Speed|Size|Locator"` for channel count.
2. Governor, turbo state, and any pinning used.
3. The regression `α ± SE` **and** the directly measured `t_s / T`; they should agree when `P ≤` physical cores.
